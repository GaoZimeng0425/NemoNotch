# 通知中心 → toast 卡片 设计

日期:2026-10-30 · 状态:待用户批准

## 意图与为什么

用户最常用的三个 app——Apple Mail、Slack、微信——的通知都进系统通知中心,但用户**不看通知中心**,横幅一闪就过,消息因此漏看。用户已经习惯刘海下方的 toast 卡片(AI 完成提醒:色环、5 分钟、点击跳 app),希望这三个 app 的通知也以同样的卡片出现;刘海左右两侧的旧「通知徽章」(读 Dock 红点)不再显示。

成功 = 不打开通知中心也不会错过这三个 app 的新消息;点一下卡片就到对应 app;处理过的通知不会再冒出来。

## 目标

- 读取通知中心里**指定 app** 的新通知,在 toast 行里显示。
- 每个 app 一张卡;卡片内容按条数切换(见「卡片内容」)。
- 点击卡片 → 打开该 app、卡片关闭、该卡包含的通知记为「已处理」,即使它们仍在通知中心里也不再生成卡片。× 同样记为已处理,但不打开 app。
- 撤掉刘海两侧的通知徽章与 Dock 红点轮询。

## 非目标

- **不从通知中心删除通知**(只读;见「约束」)。通知中心里那条由 app 自己清(Slack/微信通常在用户读后自行撤回,未实测)。
- 不深链到具体会话/频道/邮件(通知的点击动作只有通知中心能触发;我们只打开 app)。
- 不做回复、标已读等操作。
- 不为通知卡加刘海辉光。

## 反目标(技术上能用但算失败)

- 一启动就把通知中心里积压的几百条通知全刷成卡片。
- 点过/关过的通知又冒出来。
- 微信一阵消息把 AI 完成卡全部挤掉的同时,还每条一张卡——必须按 app 归一。
- 任何写入系统通知数据库的行为。
- 读不到(无权限/格式变了)时静默失效,用户以为「最近没消息」。

## 约束(已查证)

- **没有公开 API 读别的 app 的通知**:`UNUserNotificationCenter.getDeliveredNotifications` 只返回**调用者自己**的通知(Apple 文档原文 "your app's delivered notifications",ctx7 查证);`usernoted` 的私有 XPC 需要 Apple 私有 entitlement。
- **数据源**:`~/Library/Group Containers/group.com.apple.usernoted/db2/db`(sqlite,WAL 模式;部署目标 macOS 26.4,只有这一路径)。本机 macOS 27.0.1 实测:
  - 表 `app(app_id, identifier)`、`record(rec_id, app_id, uuid BLOB, data BLOB, request_date, delivered_date, presented, style, …)`;`delivered_date` 是 CFAbsoluteTime。
  - `record.data` 是 binary plist:`app`(bundle id,大小写与 `app.identifier` 可能不同,如 `com.tencent.xinWeChat` vs `com.tencent.xinwechat`)、`uuid`(16 字节)、`req.titl`/`req.subt`/`req.body`/`req.iden`、`date`。
  - Slack 有 title(发送人)/subtitle(频道)/body;微信 body 是「你收到了一条…」(微信自身「通知显示消息详情」关着时的隐私文案,无 title)。
  - 用户清掉的通知会从 `record` 删除(当前 197 条 = 通知中心现存)。
  - Mail 已登记(`app_id=3`, `com.apple.mail`)但测试邮件未产生记录,系统日志里 Mail 也没发通知——Mail 自身的通知范围设置所致(推断,未验证),不影响本设计。
- **权限**:读该库需要「完全磁盘访问权限」(终端已有故可读;NemoNotch 需用户授予)。格式是 Apple 私有、可能随系统升级变化。
- **流量**(实测峰值):微信 55 条/小时,Slack 13 条/小时。
- 仓库不变量照旧适用:主线程外 sqlite、`SQLITE_OPEN_READONLY`(zcode quota 先例);权限只在用户动作处请求、被拒静默探测不重试;轮询只记状态迁移;toast 现有不变量(Core Animation 环、按 `toastKey` 一卡、上限 4 顶最旧、5 分钟、悬停暂停、每屏显示、跳转目标在入队时快照)。

## 方案(已拍板:A)

| | 做法 | 取舍 |
|---|---|---|
| **A. 只读通知数据库**(选中) | 只读打开 usernoted 的 sqlite,文件变化触发重读 + 低频轮询兜底,按 `uuid` 判新 | 每条有唯一 ID,「已处理」精确;有标题/正文/bundle id;勿扰时也进库不漏。代价:要完全磁盘访问权限;私有格式 |
| B. AX 读屏幕横幅 | 监听通知中心进程窗口,横幅弹出时读文字 | 只要已有的辅助功能权限;但勿扰/专注/「无」样式时漏,无唯一 ID 去重只能猜,依赖横幅 UI 结构更脆 |
| (排除)公开 API / 私有 XPC | — | 见约束,做不到 |

用户选 A:B 的漏读与「不看通知中心也别错过」的目的相冲突。

## 已拍板的行为

1. **数据源 A**,只读。
2. **与 AI 完成卡共用 4 个卡位**(超出顶最旧,规则同现有队列)。
3. **按 app 归一**:每个 app 至多一张卡;同一 app 的新通知就地刷新这张卡。
4. **卡片内容 = 方案 B**(浏览器原型中选定;原型存档 `docs/superpowers/specs/2026-10-30-notification-toast-mockup.html`,选项 B):
   - 单条:头部 app 图标 + app 名;第一行 发送人(title)·subtitle;第二行 正文。
   - 多条:头部 app 图标 + app 名 + 红色计数;第一行 去重后的发送人列表(按最新在前,超宽截断);第二行「最新:<发送人> — <正文>」。
   - 卡高保持现有 66pt,整排高度一致。
5. **点卡片** = 打开该 app + 关卡 + 卡内全部通知记为已处理;**×** = 关卡 + 记为已处理。
6. **启动基线**:第一次成功读取时通知中心已有的记录全部视为已见,不出卡;之后新出现的 `uuid` 才出卡。
7. 撤掉刘海两侧的通知徽章与 Dock 红点轮询。

## 留给实现者的决定(我的默认,标注为我的判断)

- **卡片里装什么**:该 app 所有「未处理」的通知 = 启动基线之后出现、仍在通知中心、且没被点击/×/到期处理过的。计数、发送人列表、「最新」都从这个集合算。*我的判断。*
- **被挤出卡位 ≠ 已处理**:4 个卡位满了被顶掉的通知卡,里面的通知保持未处理;该 app 下次来新通知时随新卡一起回来(不立即重新入队,免得和 AI 卡来回互顶)。到期才算处理——用户有过 5 分钟看它的机会,被挤掉的没有。*我的判断*,依据「不错过」这一目的。
- **开关**:独立开关「通知中心消息转 toast」,与「完成闪光」开关互不牵连(现有 `showCompletionToast` 被 `completionFlashEnabled` 门禁,通知卡不能走这道门)。默认**开**——没有完全磁盘访问权限时它什么都不做,真正的启用动作是用户授权那一下,符合「权限只在用户动作处」。*我的判断。*
- **设置迁移**:新 UserDefaults key 存「通知转 toast 的 app 列表」,默认 Mail / Slack / 微信;旧的 Dock 红点列表 `monitoredApps` 随 Dock 轮询一起删除,不迁移(语义不同)。*我的判断。*
- **外观**:通知卡与 AI 卡同壳(同尺寸、同 Core Animation 色环、同 ×),区别只在头部图标与计数。*我的判断。*

- **监控 app 列表**:复用设置里现有的「通知 app 列表」页并改语义为「哪些 app 的通知进 toast」,默认 Mail / Slack / 微信。bundle id 比较**不区分大小写**(实测大小写不一致)。*我的判断。*
- **通知从通知中心消失时**(record 被删,如 app 自行撤回或用户在通知中心清掉):从卡里移除;卡里一条不剩则卡消失。*我的判断*——跟随系统真相,用户在别处处理过就不该再挂着。
- **卡片到期**:5 分钟,同现有;同 app 来新通知时重新计满。到期的通知记为已处理(不会因为后续刷新又以旧条目回到卡里)。*我的判断。*
- **已处理集合只放内存**:重启后靠启动基线天然不重复,无需落盘。
- **跳转**:复用 `CompletionJump`(只填 `hostBundleId`)和 `AppActivator.activate`;app 未运行时由 NSWorkspace 启动。
- **不触发辉光、不动闪光节流**:走 toast-only 入口(同番茄钟)。
- **变化检测**:监听 db 目录/`db-wal` 的文件事件,另加低频(如 15–30s)兜底轮询;读库在主线程外。检测与轮询节奏由实现者定,前提是 Slack/微信消息到达到出卡的延迟在几秒内。
- **权限 UX**:设置页用现有 PermissionCard + 拖拽授权引导(Full Disk Access 已在支持的 8 个 pane 内);未授权/读失败/格式不认识时,设置页如实显示原因,日志只记状态迁移。
- **解析失败的单条记录**:跳过并记 debug,不影响其他记录。
- **测试**:纯逻辑可测部分——plist 记录解码、新 uuid 判定(基线/已处理/已删除)、按 app 归一与卡片内容(单条/多条两行文案)、队列共用卡位——用 Swift Testing;sqlite 文件读取与文件监听不进单测。

## 风险

- macOS 升级改了库格式/路径 → 功能失效。缓解:失败如实显示,不静默。
- 读用户隐私数据:只读、只读白名单 app、不落盘内容、不出网。
